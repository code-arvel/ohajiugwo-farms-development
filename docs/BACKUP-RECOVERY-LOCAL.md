# Independent encrypted backup and recovery — local implementation

Implemented locally on 21 November 2026. **Scheduling, hosted storage, provider credentials, missed-heartbeat alerts and hosted restore remain unconfigured.** No workflow is installed or enabled. Storage selection and any billing exposure remain owner decisions. Local fixture success does not establish off-site recovery or launch readiness.

## Run the disposable drill

```sh
node --test --test-concurrency=1 tests/operations/backup*.test.mjs
node scripts/backup-fixture.mjs --fixture
node scripts/restore-fixture.mjs --fixture-root /tmp/farm-backup-fixture-RETURNED_SUFFIX
```

The backup command allocates a new owner-private temporary directory, writes deliberately non-sensitive fixture content and encrypted objects, and returns only its path/set ID. The restore command accepts only that marked temporary fixture and creates a distinct new isolated database directory. It executes the fixture SQL in PGlite, queries the actual restored row, compares exact original photograph bytes, checks structured content and records security review requirements. Neither command accepts live database/provider options, reads environment variables, contacts a provider, sends a heartbeat, restores into an existing database or publishes content. Remove the returned temporary fixture directory after inspection. The fixture-only key lives in its separate `owner-keys/` directory; this is disposable testing, not the production recovery-material arrangement.

## Integration contract

`operations/backup/index.mjs` exposes:

- `createBackup({ enabled, source, destination, ownerKey, keyId, heartbeat?, now? })`. Disabled unless `enabled === true`; returns `{setId, createdAt, verified:true}` only after readback/authentication of the saved manifest and every referenced chunk. Heartbeat runs last, with three attempts; failure throws even when a usable set was saved. The hook receives identifiers/status only.
- `restoreBackup({setId, destination, ownerKey, keyId, target})`. Requires `target.isolated === true`, a distinct identity from both source and backup destination, and all four callbacks below. Authenticates the whole set before any target callback, then streams the database/originals. A later target write failure remains a failed restore, never a successful switch.
- `retainBackups({destination, ownerKey, keyId})`. Keeps the union of newest sets in seven UTC calendar-day buckets, four Monday-start UTC week buckets and three UTC month buckets. Multiple tiers may share a set. Verifies retained data before deleting old manifests, then deletes only unreferenced objects in the configured encryption-key namespace. An unreadable manifest aborts deletion. No sets exist means orphan objects in that namespace may be reclaimed.
- `selectRetention(manifests)` is the pure bucket selector.

`source` has an independent stable `identity`, `snapshot()` and `openMedia(ref)`. Snapshot returns `{database, content, schema, releases, securityInventory, media}`. Database is a Buffer or async iterable of byte chunks. The structured metadata must be JSON serialisable and at most 16 MiB. Each media inventory record requires immutable `id`, `version`, and lowercase SHA-256 `checksum`; optional provider path stays source-side. `openMedia()` returns original bytes/async iterable, never a public thumbnail. Content/revisions, migration names/SQL/checksums, current/recent release inventories and separately captured relevant Auth identities/memberships belong in snapshot metadata. The integration must obtain these from one consistent database snapshot; this coordinator does not infer schema or query the live application.

`target` provides `restoreDatabase(asyncByteIterable, {securityDataActivation:false})`, `restoreContent(content,{schema,releases})`, `writeMedia({id,version,checksum}, asyncByteIterable)`, and `recordSecurityReview(data)`. Security inventory is sent to review with **enforced** `activationAllowed:false` and `sessionsMustBeReset:true`. It is never passed to `restoreContent`. Restore adapters must consume each stream fully and must not activate memberships, sessions or provider credentials. The library's identity/isolation checks are an adapter contract; the supplied executable CLI enforces this by exposing fixtures only. No production restore adapter or general-purpose restore CLI is provided.

## Storage, encryption and consistency

Database and photograph bytes are processed in bounded 1 MiB chunks. AES-256-GCM uses a fresh random 96-bit nonce and authenticates the complete storage key as AAD; encrypted envelopes include their tag. Whole-stream and individual-chunk SHA-256 hashes, sizes, source identity, timestamp, schema/content/release/security metadata, media IDs/versions and key identifier are authenticated through the encrypted set manifest. Metadata and manifest buffers are capped at 16 MiB; stream references are capped at 100,000 chunks per object. A single incoming provider chunk is owned by its transport; providers should also stream bounded buffers.

Immutable photographs found in a prior authenticated set reuse their existing chunk references, so unchanged originals are not downloaded again from source Storage. A changed checksum for an unchanged ID/version fails. Database/metadata chunks also deduplicate by hash. Every reused object is read back and authenticated from backup storage before success; storage deduplication never bypasses verification. Only encrypted bytes go to the destination. Hash-based object keys reveal equality/size; the bucket must remain private. A partial dump creates no recovery set or heartbeat; interrupted uploads can leave unreferenced encrypted objects for later locked garbage collection. Corrupt existing immutable objects cause failure and require maintainer investigation, not silent overwrite.

All backup, restore and retention operations require the same exclusive destination lock. Retention and creation cannot race. The supplied S3 implementation uses conditional lock creation and never steals an abandoned lock. Maintainer inspection must prove the old runner stopped before removing one; there is no unsafe automatic expiry takeover. A process-local mutex is insufficient. Filesystem fixtures use an exclusive lock directory and fail closed on a stale lock. Inspect stale locks before removal. Object operations retry at most three times. The injected hosted transport must enforce bounded request deadlines and must reject partial/incomplete listings; there is no automatic infinite retry.

The 32-byte `ownerKey` and non-secret `keyId` are explicitly injected. No operation reads secrets from process environment or emits raw exports/credentials to logs. Recovery keys are independent of bucket/source credentials and must remain owner-controlled, with emergency access and a secure recovery inventory; never store them in the bucket, repository, Actions artifacts/cache or logs. The symmetric implementation needs transient key access for authenticated verification; the production runner's key-delivery/rotation design must be approved before scheduling. Separate storage prefixes/destinations are required for key rotation; mixed-key set manifests fail closed until an explicit multi-key migration/recovery process is provided. Retain old recovery keys as long as their sets are retained.

## Prepared provider boundaries

`operations/backup/adapters.mjs` provides code-only adapters:

- `pgDumpSource`: requires an absolute `pg_dump` binary path, explicitly supplied connection environment, independent source identity and a `snapshotProvider()`. The provider exports a Postgres snapshot and returns `{snapshotId, inventory, release}` while retaining its transaction until dump completion. Dump runs without a shell or inherited environment, uses custom format, selected public/private application schemas, excludes active membership/session/invitation/auth-attempt/provider-effect/cleanup-job data and omits ownership while preserving ACL statements. Nonzero exit/timeout fails even if bytes were received; stderr is not logged. Auth/membership recovery inventory must be exported separately through the snapshot provider. Provider roles, Auth schema, secrets, privileges and complete RLS/restore compatibility remain explicit hosted drill responsibilities. This adapter has only been exercised with an injected process transport; no actual hosted dump was run.
- `privateMediaSource`: uses injected snapshot/download callbacks and an explicitly private bucket. Only immutable original paths found in the saved inventory can be downloaded. Provider ACL/RLS and checksum provenance must be verified during hosted setup.
- `scopedS3Destination`: uses injected signed `transport.put/get/list/delete`, bucket, dedicated prefix and exclusive `withLock`. Every write requests private ACL and `If-None-Match: *`; only precondition status 412 is treated as existing content and that content is subsequently verified by the coordinator. Lists are paginated and reject scope escape/repeated cursors. The transport must implement complete consistent listings, bounded streaming/download size/deadline, signed private requests and conditional-write semantics. A bounded SigV4 HTTPS transport and private-original downloader are supplied locally; no real credentials/account, R2 subscription or destination has been configured or activated. R2 does not support object ACLs: the operator must independently verify bucket privacy.
- `filesystemDestination`: private local fixture destination with exclusive creation, file mode 0600, directory mode 0700 and lock directory. Use a dedicated owner-controlled fixture directory, not an attacker-writable/shared existing directory.

An authenticated short-lived administrator export endpoint may use this source/coordinator boundary behind existing fresh membership/session checks and an authorised private download mechanism. This module does not itself expose any HTTP or public download endpoint. Never publish encrypted or plaintext exports as website assets.

## Remaining hosted recovery gates

Before enabling anything: name the accountable backup owner and technical maintainer; choose/approve independent private storage and metering; approve scheduler and transient key access; scope source/destination credentials and durable exclusive lease; validate database connection/pg_dump version and snapshot provider; measure compressed database size, Storage export egress and retained size; select an independent missed-heartbeat alert with a 36-hour overdue boundary and verify actual notifications. Do not upload backups to workflow artifacts/caches. GitHub schedules are best-effort, not a 24-hour guarantee.

Before launch and quarterly: perform a separately approved isolated hosted restore of actual schema/RLS, content/revisions, relevant Auth identities, **reviewed** memberships and exact original photo bytes; reset sessions/secrets, inspect revoked users, rebuild/compare public output and record measured recovery time. Restore is a draft/recovery operation and never automatically publishes or replaces production. Keep the last successful static site online while recovering. No hosted database dump/restore, alert notification, scheduled laptop-off run or off-site restore has been proved by this implementation.

## Prepared live runner (not executed)

`node scripts/run-backup-worker.mjs --confirm-project <project-reference>` requires exact independent-destination approval, verified private storage, owner-controlled 0600 recovery-key/passfile files, verified TLS, project-bound direct or session-pooler database configuration, explicit absolute PostgreSQL binaries and scoped S3 settings. The runner does not load or change `.env.admin`. Its source holds a repeatable-read exported snapshot while `pg_dump` runs, downloads original immutable photos, encrypts and verifies uploads, then sends an optional strictly scoped heartbeat and performs locked recovery-set retention. The schema dump preserves privilege statements, excludes active security/session/provider-effect data, and records separate sensitive security recovery inventory under encryption. Managed Supabase roles/Auth compatibility requires an actual isolated provider restore drill. Credentials and raw provider/process output are withheld from reports.

`hosting/templates/backup-workflow.yml.example` is a prepared executable manual-run template, deliberately inactive and gated pending destination/key/scheduler decisions. It is not evidence of an installed job. No production `pg_restore` adapter that could activate old identities/memberships is exposed; full provider disaster recovery remains a reviewed maintainer operation. Local restore fixtures verify cryptographic/stream/target separation contracts only. Do not call them a completed hosted restore.
