# Browser password confirmation — local integration

The existing session form now has a protected `/admin/confirm-password` mode, linked from the session page. It reuses the approved cream/green form, logo, local typography, flat spacing and ordinary mobile scrolling. Acceptance/public/editor design files are unchanged. No arbitrary return URL, recipient input or automatic account-management action is introduced.

A verified session supplies identity/CSRF. Only explicit POST `/admin/api/reauthenticate` sends the current password; the existing service performs checks/rotation. A 401 is treated as correctable only after a session GET verifies the exact original identity and CSRF; changed/ended/unknown context requires reload. Correctable password errors stay by the field and preserve its value. Rate errors are generic. An explicit matching-user/rotated-CSRF response confirms success, clears password/identity and removes stale instructions. A missing/uncertain/503/CSRF result clears the field, hides submission and offers **Reload password confirmation**. It never infers a successful confirmation from an ordinary session GET, automatically repeats the POST or continues a privileged operation. Reload obtains fresh server-verified session context; it does not prove the previous attempt succeeded.

The shared pagehide/pre-import/restored-page lifecycle guards remain active. CSRF/identity metadata is consumed from DOM and removed; no credentials/provider tokens go to browser storage or response bodies. APIs remain default-disabled through the hosting development gate; live bootstrap remains disabled. Future sensitive SQL must still enforce membership and five-minute recency in its own transaction.
